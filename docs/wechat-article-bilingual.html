一个 Lambda 搞定多账户 Bedrock 监控：成本、Token、延迟、配额——还能看出账户是否被封

One Lambda to Watch Them All: A Near-Zero-Cost Multi-Account Amazon Bedrock Dashboard — Cost, Tokens, Latency, Quotas, and Even Account Health.

如果你在管多个 AWS 账户上的 Claude / Bedrock 业务，大概率遇到过这几个问题：切控制台切到手软、成本和调用量对不上账、Marketplace 订阅的 Claude 费用在 Cost Explorer 里「隐身」、还有——某个客户账户悄悄被停用了，你是最后一个知道的。

这篇文章介绍我们开源的一套极简监控面板：1 个 Lambda + 1 个 API Gateway HTTP API，月成本约等于 0，却能把多账户的模型 Token 用量、调用次数、延迟、成本、服务配额一屏打尽。文末还附赠一个隐藏技巧：用配额查询间接探测「账户是否被封」。

ENIf you run Claude / Bedrock workloads across multiple AWS accounts, you have probably suffered from console-hopping, costs that never reconcile with usage, Claude Marketplace charges that "hide" in Cost Explorer — and finding out a customer's account got suspended long after the fact. This post walks through our open-source, minimal dashboard: one Lambda + one API Gateway HTTP API, roughly $0/month, covering tokens, invocations, latency, cost and service quotas across accounts — plus a hidden trick: using quota queries as an account-health probe.

01 为什么需要它 · Why We Built It

市面上的方案要么太重（Grafana + 采集器 + 数据库），要么太贵，要么只看单个账户。我们的需求很朴素：

  • 多云账户：多个客户账户的 Bedrock 用量要一起看；
  • 零运维：不想维护服务器、数据库、采集 Agent；
  • 成本可见：On-Demand 和 Marketplace 订阅的 Claude 费用都要算进来；
  • 凭证不落服务端：客户密钥绝不能存在我们的基础设施里。
ENExisting options were either heavy (Grafana + collectors + a database), costly, or single-account only. Our requirements were simple: multi-account visibility, zero maintenance, cost coverage for both on-demand and Marketplace subscriptions, and zero server-side credential storage.

02 极简架构 · The Minimal Architecture

整套系统只有 4 个 CloudFormation 资源：1 个 IAM Role、1 个 Lambda、1 个 Lambda Permission、1 个 API Gateway HTTP API。前端页面在构建时直接内联进 Lambda 代码，页面与查询 API 同源，打开即用、零配置。

几个设计取舍：

  • Lambda 代码超过 CFN ZipFile 内联上限（4096 字节），因此从 S3 引用 zip，模板仍是「控制台可直接部署」；
  • Lambda Function URL 在部分组织被 SCP 禁止（403），改用 API Gateway HTTP API 规避；
  • Lambda 执行角色只有写日志权限，所有查询用调用方上传的密钥执行。
ENThe entire stack is 4 CloudFormation resources. The frontend is inlined into the Lambda code at build time, so page and API are same-origin — zero client configuration. The Lambda's execution role can only write logs; every query runs with the caller-supplied credentials.

04 隐藏技巧：账户健康探针

面板里的服务配额表（默认查 Bedrock 的 L-D06938E7）其实还藏着一个实用玩法——间接判断账户是否被封 / 受限：

✅ 能正常返回数值 → 密钥有效、账户状态正常、API 可调用
❌ AccessDenied / 账户级错误 → 可能密钥失效、账户欠费停用（被封）、或被组织策略限制
💡 悬停报错单元格可看具体错误信息，帮助进一步定位。

更进一步，「账户健康探测」表还引入了两个信号：

  • STS 身份：后端自动调 GetCallerIdentity 读取真实 Account ID——所以添加账户连名字都不用填，账户名自动就是账号 ID；
  • CloudShell 探测（只读）：当账户被 AWS 风控时，控制台打开 CloudShell 会报「无法创建环境。正在验证您的账户」，而此时 STS 和成本查询仍然正常——也就是说，只有 CloudShell 的只读 API 能暴露这个状态。面板把它做成了一列：✓ 可用 / ⚠️ 账户验证中（疑似被风控）。

对同时管理多个客户账户的团队来说，每天扫一眼这张表，谁家账户出问题立刻知道，而不用等客户来问「为什么我们的模型调不通了」。

ENHidden trick: the quota table doubles as an account-health probe — a successful quota read means the credential works and the account is in good standing; AccessDenied or account-level errors often mean a dead key, a suspended account, or SCP restrictions. The dashboard adds two more signals: STS identity (auto-reads the Account ID — you don't even type an account name when adding one) and a read-only CloudShell probe. When AWS puts an account under risk-control verification, the CloudShell console shows "We couldn't create the environment. We're verifying your account" — while STS and Cost Explorer still work fine. Only the CloudShell API reveals that state, so the dashboard surfaces it as a per-account status column.

05 踩坑实录 · Seven Pitfalls We Hit

这套小面板的迭代过程几乎是一部「AWS 冷知识合集」，每一条都是真实踩过的坑：

坑 & 解法 · Pitfalls & Fixes
CFN ZipFile 内联上限 4096 字节 Lambda 代码改从 S3 zip 引用
Function URL 明明配了 AuthType=NONE 仍 403 组织 SCP 禁止公开 Function URL → 换 API Gateway HTTP API
模板报循环依赖（Api ↔ Permission） 删掉显式 DependsOn，SourceArn 引用已隐含依赖
Marketplace 版 Claude 费用按 SERVICE="Amazon Bedrock" 过滤为 $0 改 GroupBy=SERVICE，匹配名称含 "bedrock" 的所有服务
CE 小时粒度要求完整 datetime 格式，且是 PAYER 端 opt-in 失败自动降级 DAILY
CloudWatch 里调用次数指标查 InvocationCount 为空 实际指标名是 Invocations（复数，没有 Count）
SEARCH() 返回的 Label 不含 ModelId= 前缀，解析全失败 单维度时 Label 是「模型ID 指标名」，按空格取首段
ENBuilding this dashboard turned into a greatest-hits collection of AWS trivia: the 4 KB CFN ZipFile cap, SCPs silently blocking public Function URLs, CFN circular dependencies, Marketplace Claude charges hiding under their own service names, hourly CE granularity being a payer-account opt-in, the metric being Invocations and not InvocationCount, and SEARCH() labels not containing ModelId=. All documented in the README.

06 安全设计 · Security Model

「自助上传密钥」听起来吓人，但这套方案的安全边界其实很清晰：

  • 密钥只存在浏览器 localStorage（可选，默认仅会话内有效），服务端从不落盘；
  • 上传密钥只需 4 个只读权限：cloudwatch:GetMetricData、ListMetrics、ce:GetCostAndUsage、servicequotas:GetServiceQuota；
  • Lambda 执行角色零数据面权限，删栈即烟消云散；
  • 生产建议：专用 IAM 用户 + STS 临时密钥。
ENCredentials live only in the browser (session-only by default); the server never persists them. Uploaded keys need just four read-only actions. The Lambda's own role has zero dataplane permissions. Recommended hardening: dedicated IAM users + STS temporary credentials.

07 三步部署 · Deploy in Three Steps

# 1. 构建包（前端内联进 Lambda）
python deploy/build-template.py

# 2. 上传到任意同区域 S3 桶
aws s3 cp deploy/lambda.zip s3://<你的桶>/lambda.zip

# 3. 部署（或控制台直接上传 cfn/template.yaml）
aws cloudformation deploy \
  --template-file cfn/template.yaml \
  --stack-name bedrock-dashboard \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides \
    LambdaCodeBucket=<你的桶> LambdaCodeKey=lambda.zip

栈创建完成后，输出里的 DashboardUrl 打开即用。删除也只要一条 delete-stack——因为服务端不存任何状态。

ENBuild, upload the zip to any S3 bucket in-region, deploy the CloudFormation template (console or CLI). Open DashboardUrl from the stack outputs and you are done. Tear down with a single delete-stack — nothing persists server-side.
